# 什么算架构（第一课）

> 你说「我不懂架构，你可能得从头教我」。**那就从头。** 但我不会给你教材第一章——因为「从第 1 页开始读」正是这套方法里写明的反模式；而且架构不是背出来的知识，是**判断**，判断只能从你自己手上的系统里长出来。
> 说明：我按「**软件/系统架构**」理解你的意思（不是建筑设计）。如果不对，说一声，我换。

## 一、类比：先给你一个能挂东西的钩子

你装修过房子吗？

- **刷墙、换沙发、贴壁纸**——随便改，改坏了也就难看几天。这叫「实现细节」。
- **承重墙、水管主管、电路进户**——动一处，整栋楼跟着动，还可能出事。**这叫架构。**

所以第一句话：**架构 = 你很难改的那部分。**

判断标准很简单，只有一个：**改动代价**。不是"重要程度"，不是"听起来高不高级"——是**你敢不敢改、改一次要动几处、改完怕不怕出事**。

## 二、最小定义（三句话，先只记这三句）

1. **架构 = 系统里那些一旦定下来、改动代价很大的决策集合。**
2. 它大致包含四样东西：**切成了哪几块**（部件）· **块之间怎么说话**（接口/关系）· **数据放在哪、谁拥有它** · **跑在哪、依赖谁**（部署与外部依赖）。
3. 每个这样的决策都在**买一种能力、卖另一种能力**——快、稳、好改、省钱，四个基本只能少要。这就是**权衡**（trade-off）：*没有代价的好处，都是假的。*

> 上面出现的词，先用你自己的话理解就够，**不用现在背**：部件 = 能单独说清楚的一块；接口 = 两块之间约定的说话方式；质量属性 = 快/稳/好改/省钱这四类"好不好"；技术债 = 当初为了快欠下的、以后要还的账。

## 三、立刻动手：三个问题（这就是你的起点诊断）

不要看书，不要查资料。**看着你自己的系统**（比如 DoggyArium 论坛项目，或微微电商那套），用你自己的话回答：

1. **哪一部分改起来最贵？**
   （改一次要动好几处、或者改完心里发虚的那个地方。例：用户表？订单状态？权限？消息通知？）
2. **如果用户量涨 10 倍，最先坏的是哪里？**
   （慢了？崩了？数据对不上了？——这暴露你系统现在最虚的那项能力。）
3. **明天要加一个「私信」功能，你会动哪几个地方？**
   （答"新加一个模块就行"是一种答案；答"得动用户表、还得动通知和权限"是另一种答案——两种都对我有用。）

**这三个答案合起来，就是你系统的架构草图**——不是名词表，是**代价表**。

> 答不出来也没关系，**答不出来本身就是诊断结果**：说明你对自己的系统还没有"结构视角"，那正是我们要练的第一件事。你可以只答一个。

## 三点五、把镜头对准你自己的系统（第一手材料，不是假设）

我读了你库里的两份原始文档（只读，未改动）：`论坛社区项目生态系统架构图.md`、`智能体论坛系统架构框架.md`（其状态标着 `draft`）。**它们已经是一份架构**——只是还没成为「你能辩护的架构」。用上面的镜头过一遍：

### ① 切成了哪几块（部件）

| 那份文档里的层 | 用第一课的话说 |
|---|---|
| 用户界面层（Web/App） | 门面 |
| API 网关层 | 大门与门卫（入口、路由、认证） |
| 智能体协调管理层（注册发现 / 任务队列 / 状态监控 / 调度中心） | **承重墙候选 1**：所有智能体调用都过它 |
| 智能体执行层（内容审核 / 版主 / 用户服务 / 运营 / 应急 五类集群） | 干活的五支队伍 |
| 数据与知识层（关系库 + 向量库 + 规则知识库 + 缓存 + 搜索 + 对象存储） | **承重墙候选 2**：数据归谁、几套库并存 |

### ② 它已经做了哪些权衡（每个选择都在卖东西）

| 它选择了 | 它买到的 | 它卖掉的 |
|---|---|---|
| 中心化协调管理层 | 统一调度、状态可见、易插入新智能体 | 中心单点与瓶颈；协调层一挂全挂 |
| 五类智能体集群 + 池化水平扩展 | 各司其职、可扩缩容 | 调试与可观测性成本；跨智能体一致性 |
| 多套存储并存（关系 / 缓存 / 向量 / 搜索 / 对象） | 各用其长（事务 / 缓存 / 语义检索 / 全文 / 文件） | 数据一致性、备份与迁移成本、运维复杂度 |
| 合规架构（实名 + 内容安全 + 审计日志） | 过审、可追溯 | 转化率与体验（每步多一道门） |

### ③ 三个问题，用你自己的系统回答

1. **哪一部分改起来最贵？** 我的读法：**数据归属**——帖子 / 画像 / 检索索引分散在关系库、向量库、缓存之间，改一个字段常要同时改同步逻辑与索引。**但这只是我的读法，你可以反驳。**
2. **用户涨 10 倍，最先坏在哪？** 我的读法：**协调管理层**（中心调度 + 队列）与**向量检索的成本/延迟**，而不是界面层。依据：文档把状态监控、任务队列、调度集中在一层，且检索依赖独立向量库。
3. **明天要加「私信」，要动哪几处？** 我的读法：数据模型（会话/消息）＋ 权限与实名校验 ＋ 通知（可能要新增一类队列主题）＋ 网关路由 ＋ 前端；而**「要不要新增一类『私信智能体』」才是真正的架构决策**——它决定私信是"一个功能"还是"一支新队伍"。

> 注意这里的教法：我不是给你标准答案，而是**先做一次示范**——**你能反驳我哪一点，比我讲对哪一点更有价值**。文档上写着 `draft`：它现在是「一份存在的文档」；只有当你能为每一堵承重墙辩护（或推翻）时，它才变成**你的**架构。
## 四、从零到能判断：三层台阶（不按教材顺序）

| 台阶 | 能力 | 检验方式 |
|---|---|---|
| **1. 认得** | 能说清你系统的部件与关系 | 上面三问能答出来 |
| **2. 判断** | 能说出一个选择的**代价**，以及它锁死了哪项能力 | 拿一个你做过的决策，说出你卖掉了什么 |
| **3. 改变** | 能在两个候选结构里做一次有依据的选择，并写下**推翻条件** | 一次真实的改造决策 + 别人挑刺挑不倒 |

**只有第 3 层算"会架构"。** 而它必须踩过 1 和 2——这也是为什么我先问那三个问题，而不是先讲微服务、DDD、云原生（那些都是第 2、3 层才需要的东西）。

## 五、我这边的教法（先说清，免得你等错东西）

- **一次只教一个概念 + 一个动手动作**；下一个教什么，**由你的答案决定**，不由教材目录决定。
- **每个术语当场定义**，不要求你先背；你哪天能用它自己的话说清，它才算进你的词汇。
- **不给菜单、不预设你的水平**；你答多少，我就据实往哪走。
- **不给你 12 周计划**——那是备考的做法（我们已经否掉过一次）。

## 中文速览

- **架构 = 你很难改的那部分**（类比：装修随便改，承重墙一动整栋楼动）。判断标准只有一个：**改动代价**。
- 三句话定义：①难改的决策集合 ②含四样：切块 / 怎么说话 / 数据归谁 / 跑在哪 ③每个决策都在**买一种能力、卖另一种能力**——没有代价的好处都是假的。
- **立刻动手（三个问题）**：①你系统里哪部分改起来最贵？②用户涨 10 倍最先坏在哪？③要加「私信」你会动哪几处？——**这三个答案就是你系统的架构草图**。
- 三层台阶：**认得 → 判断 → 改变**，只有第三层算「会架构」。
- 教法承诺：一次一个概念 + 一个动作 · 术语当场定义 · **不给菜单、不给 12 周计划** · 下一课由你的答案决定。
