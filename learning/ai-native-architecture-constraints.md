# AI-Native Architecture Constraints

> **来源说明**：本模型由学习者三条回答 + 本轮"AI 原生用人观"合成。**原料是他的**（引文未改）；**合成的两个约束与三处收窄是我的判断**（已标注 `[推断]`）。用途：把他的直觉变成**能被评审的表述**。

## 一、原料：他说的三件事

1. 选 Rust 的理由：**编译期报错/警告让 AI 清晰感知、明确下一步**（vs Python 缩进对 AI 难判层级、解释型产生冗余文件）。
2. 用户量 100→1000 先坏的不是运行，而是**边际成本**：发帖→Agent 回复→token 激增；对象存储成本日增→媒体看不见。
3. **「未来云原生、AI 原生时代，我们要招的不是程序员，而是更优秀的 AI。」**（并承认 Rust 程序员不好招）

## 二、合成：两个第一性约束 `[推断]`

```text
约束一（选型层）：建造者可验证性 —— 建造者（AI）能否低成本地知道「错了、错在哪、下一步做什么」
约束二（规模化层）：单位产出的边际成本 —— 每个用户动作换来多少 token / 存储 / 重试
```

- **约束一决定"写得对不对、快不快"**：信号强的栈（编译期检查、显式结构）→ 少猜少试；
- **约束二决定"规模上能不能活"**：成本曲线随用户动作量增长，而不是随服务器数量增长；
- 两者相连：**约束一降低每次修改的重试次数 → 直接压平约束二的曲线**（这就是他第 1 条与第 2 条其实是同一个模型的原因）。
- 人类人才池**不再是第一性约束**——这是他对的地方。

## 三、人类角色：三件不可外包的事 `[推断]`

| 不可外包 | 为什么 |
|---|---|
| **验收（verify at the boundary）** | AI 的失败是**静默**的：它会给一个看起来完整的答案。越强的模型，错误越稀少、越不像错误，因此越需要在边界上验 |
| **担责（accountable sign-off）** | 法律与合规责任附着于人或公司，不附着于模型。他的系统本就有 **实名 / 内容安全 / 审计**，这些必须有人签字与值守 |
| **判断（judgement under ambiguity）** | 目标由用途定、权衡选哪一边、何时推翻决定——这些正是本运行在练的能力 |

所以准确的表述不是"不招程序员"，而是：**程序员从生产者变成验收者与责任人**。

## 四、「只招 AI 不招人」要收窄的三处 `[推断]`

1. **责任与合规不可转移**：审计日志要有人负责；出了事要有人签字。AI 不能承担法律责任。
2. **成本结构换了形态，不是消失**：人＝固定成本 + 容量上限；AI＝**可变成本 + 反馈回路**。用 AI 替代人力，等于把成本从工资单挪到**随使用量增长的曲线**上——而那条曲线正是他第 2 条回答里"先坏"的东西。
3. **新增单一依赖**：若某语言的可行性依赖**某个模型的当前能力**，模型涨价 / 下架 / 能力回退都会传导成架构风险。缓解：核心留在**可迁移的接口契约与标准库**上，并定期做"换模型能否继续"的测试。

## 五、把主张变成能测的东西（否则只是观点）

| 主张 | 可检验的推论 | 数据从哪来 |
|---|---|---|
| 选栈要看建造者可验证性 | 同等任务下，Rust 的**首次通过率更高 / 平均重试次数更少** | 他自己的 agent 会话与修复轮次 |
| 边际成本是第一性约束 | **¥/发帖、¥/Agent 回复、¥/存储·月** 能预测"先坏"位置 | 他第 2 条回答的原始账 |
| 人是验收者而非生产者 | 他能给出**验收清单**（而不是"AI 说好了就好"） | 一份可复用的验收 checklist |

## 六、边界与反例

- **建造者是人时**：人才池重新成为第一性约束（这时"Rust 难招"是硬伤）；
- **责任密集行业（金融/医疗/内容）**：验收与合规成本可能压过建造者效率；
- **一次性/小规模项目**：边际成本曲线平缓，约束二权重下降；
- **模型能力商品化后**（多模型都能干 Rust）：单一依赖风险下降，但**验证需求不降**。

## 第三轮修订：成本必须分两层（学习者的修正，2026-10-05）

**他的修正原话（要点）**：「生态不完善，Token 的消耗肯定会高，但这部分**高出的成本在于开发阶段，属于单次投入**，其 ROI 是为了服务后续长期的发展。」

**这条修正推翻了我上一版的合成**：我把"边际成本"讲成一条曲线，**混淆了两种性质完全不同的成本**。

| 成本层 | 来源 | 性质 | 记法 |
|---|---|---|---|
| **开发期一次性** | **生态不完善** → 更多自写代码、检索与试错 | **一次性投入**（capex 型），摊销到系统寿命 | 每功能多出的 token × 功能数 |
| **运行期经常性** | **产品自身的 Agent 回复 + 对象存储** | **随用户动作增长**（opex 型） | ¥/发帖 · ¥/Agent 回复 · ¥/GB·月 |

**修正后的结论**：Rust 生态缺口属于**第一层**（一次性、可摊销）；真正会"先坏"的是**第二层**（由产品行为驱动）。**两层的应对手段不同**：第一层靠**前期预算与排期**（他说的"单次投入换长期"成立），第二层靠**限额、降级、缓存与产品规则**。

**他的可验证性收益（原话要点）**：「它在写代码过程中不会出现错误代码，从而避免 CI/CD 到线上后产生生产事故。」
- 准确表述：**把缺陷左移到编译期**——编译期失败最便宜，线上事故最贵。
- **量词修正（重要）**：Rust 保证的是**内存安全 / 类型安全 / 数据竞争安全 / 穷尽匹配**等**可判定的一类**缺陷；**不保证业务语义、需求理解与算法逻辑正确**。**它抬的是下限，不是上限。**
- **指标链**：编译期捕获数 → CI 失败率 → 线上事故数 / 回滚次数 / MTTR。

**内存断言的可复核化**：他说"基线 200MB，含压测，长期不受影响"——这是一条可复核主张，但要把**压测条件**写进 ADR（并发数、数据量、Agent 并发数），否则别人无法复现；且 200MB 主要由进程常驻决定，**Agent 并发上升时的内存曲线需要单独一条数据**。
