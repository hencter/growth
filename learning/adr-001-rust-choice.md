# ADR-001：论坛后端选型采用 Rust

> **这是什么**：ADR（架构决策记录）= 把一条「很难改的决策」写成四段，让六个月后的自己和别人都能看懂当时为什么这么选、以及什么时候该推翻它。本页由师友代拟结构，**内容全部来自学习者自己的话**；未填处显式标 ⬜，不替他编。

## Context（迫使我们做决定的力量与约束）

1. 社区论坛的技术架构**改动代价很高**——选型一旦定下，后续大量工作都压在这个选择上。
2. 选型时面对的 **Rust 生态不完善**：库、示例、可复用方案少于更成熟的生态。
3. 本项目以 **AI 编码代理**为主要生产力，因此「生态不完善」的直接代价以 **token 消耗**形式出现（需要更多检索、试错与自写代码）。
4. 对 **运行成本（内存/算力）** 敏感：Rust 构建出的常驻内存约 **200MB**。

> 注：第 1–4 条均为**约束**（事实与限制），不是"Rust 更先进"这类推销词。

## Decision（我们的选择）

**我们将论坛后端的技术栈建立在 Rust 生态之上**，并**显式接受**由此带来的生态不完善成本（表现为更高的 token 消耗与更高的改造摩擦）。

## Status

**accepted**（2026-10-05 由学习者确认；此前为 proposed）

## Consequences（应用这个决定之后的世界）

| 类型 | 内容 | 来源 |
|---|---|---|
| 代价 | 生态不完善 → **大量 token 消耗** | 学习者原话 |
| 代价 | 后续**改造非常累** | 学习者原话 |
| 好处 | 内存占用低（约 200MB） | 学习者原话 |
| 好处 | 算力不再是第一瓶颈（容量侧留有余量） | 学习者第 2 条回答的推论 |
| 风险 | 成本敏感 + 生态不完善 → **边际成本被放大**；一旦发帖触发大量 Agent 回复，token 成本随帖子量非线性上升 | 学习者第 2 条回答 |
| **推翻条件（Q5 已填）** | **①迭代速度成为首要约束时**——「产品迭代需要非常快速时，TypeScript 的优势可验证：Rust 的短板是需要反复完整编译」；**②出现 AI 原生编程语言时**——「具备 Rust 的大部分特性，同时弥补其缺陷」；**③监控项：主模型长期不擅长 Rust 且无改善** → 建造者侧优势不成立 | 学习者 Q5 原话 |

## 备选方案（Alternatives）— Q1 已答

| 备选 | 它买到的 | 它卖掉的（被否的原因） | 来源 |
|---|---|---|---|
| **Python（FastAPI 方案）** | 生态很好、库齐全、上手快 | ①**缩进语法对 AI 不友好**——难以判断代码层级（结构靠空白，歧义高）②**解释型**会产生大量冗余文件，拖累上下文与 token | 学习者 Q1 原话 |
| **Rust（已选）** | ①**编译期报错 / warning 是给 AI 的清晰信号**——"明确下一步操作" ②内存占用低（约 200MB）③编译验证完整 | 生态不完善 → token 消耗高、改造累（见 Consequences） | 学习者 Q1 + 第 1 条回答 |

**这一栏为什么是 ADR 的核心**：它证明这条决策是**比较之后的取舍**，不是偏好——也是"能辩护"的第一块实证。由此提炼出的架构属性见 [[builder-verifiability|建造者可验证性]]。

## Q2 记录与事实更正（2026-10-05）

**他的 Q2 回答（要点）**：Go 被很多后端选用，但他选 Rust——理由是 **Go 的内存回收机制并不一定那么理想**；Rust「源于 C 语言之父的设计初衷」「旨在为云原生时代构建更适用的语言」；Rust 构建能力"全领域覆盖"，可用 crates 分包到桌面/服务端，未来跨平台客户端链路更顺；对 AI、对他本人、乃至**招聘 Rust 程序员**"在架构上都更具可行性"。

**判断部分：成立。** 他命中的正是第 ② 条轴（**运行期确定性 / GC**），所以 Q2 的检验目的达成：备选集已完整。

**⚠️ 事实更正（我查源后更正，附出处）**

| 他的说法 | 核实结果 | 出处 |
|---|---|---|
| 「Rust 源于 **C 语言之父**的设计初衷」 | ❌ **错误，且方向相反**。Rust 由 **Graydon Hoare 于 2006 年在 Mozilla** 创造，2009 年获 Mozilla 官方资助，2015 年发布 1.0；C 的发明者是 **Dennis Ritchie**（与 Rust 无关）。而 **C 世界的传奇人物 Ken Thompson 在 Go 的设计团队**（Griesemer / Pike / Thompson，2009-11-10 首发）——**不在 Rust** | 维基百科 Rust / Go / C 条目（2026-10-05 实测抓取） |
| 「Rust **旨在为云原生时代**构建」 | ❌ 设计目标不是"云原生"（该词晚于 Rust）：官方定位是**性能、类型安全、并发、内存安全**，并且**不使用垃圾回收**（靠 RAII 管资源）；早期驱动场景是浏览器引擎 Servo | 同上 |
| 「Go 的内存回收机制并不一定那么理想」 | ✅ **事实层面成立**（Go 确有 GC）；"理想与否"是**判断**，可接受但最好给数据 | Go 条目 |
| 「crates 可分包到桌面/服务端，跨平台链路更顺」 | ✅ 成立，是一项**真实的架构收益**（同一套库跨形态复用） | Rust 条目 + 通行工程实践 |
| 「**招聘 Rust 程序员**在架构上更具可行性」 | ⚠️ **未获支持，方向可能相反**：Rust 人才池显著小于 Go / TypeScript / Java。若要坚持需给证据，否则应改写为"对我个人与 AI 而言" | 判断（需证据） |

**为什么这条更正比错误本身更重要**：评审现场里，这一句"Rust 是 C 之父设计的"会让听众**连带怀疑你其他正确的判断**——而你的判断是对的（GC 那条就是对的）。**判断力与证据纪律是两件事**：前者你已经有，后者是这轮的训练目标。## 第二轮修订：语音转写澄清 + Go 事实核实（2026-10-05）

**学习者澄清**：上一轮那句「源于 C 语言之父的设计初衷，旨在为云原生时代构建更适用的语言」**本意指 Go（Go Lang）**，属**语音转写错误**。我未直接采信，而是按纪律重新查源，验证"改指 Go 后是否成立"。

**核实结果（2026-10-05 实测抓取）**

| 主张（改指 Go 后） | 核实 | 出处 |
|---|---|---|
| 出自 C / Unix 传统的"老将"之手 | ✅ **基本成立**：Go 由 **Griesemer / Pike / Ken Thompson** 设计（Google，2009-11-10 首发）；**Thompson 是 Unix 共同创造者，1983 年与长期同事 Dennis Ritchie 同获图灵奖**——他来自 C/Unix 世界，但**不是 C 的作者** | Go 维基 + Ken Thompson 维基 |
| 语法承接 C 风格 | ✅ 成立：原文 "simple syntax similar to C++" | Go 维基 |
| 为云原生时代而设计 | ✅ **实质成立、术语后置**：官方 FAQ 原文 "Go was born out of frustration with existing languages"；**支持网络化与多核计算**、**编译快**、治理**大型工程复杂性**，并明确"大并发程序需要垃圾回收或安全自动内存管理"。云原生一词晚于该语言，但设计要求正好命中它；Go 亦是 Docker / Kubernetes / Caddy / CockroachDB 的语言 | **go.dev/doc/faq（L0）** + Go 维基 |

**两处精确化（这样在评审里站得住）**：①「C 之父的设计初衷」→「出自 **Unix/C 传统的老将（Thompson、Pike，贝尔实验室）**之手」；②「旨在为云原生时代」→「**为网络化/多核与大规模工程而设计，恰好命中后来的云原生需求**」。

**过程教训**：该错误由**输入通道（语音转写）**引入，**说话人自己看不见**——纪律不变且更锋利：**入档前给每条主张标 [查过源] / [印象] / [推断]**。学习者一轮后**自查发现并纠正** = 正面证据（判断 / 知边界）。

## Q4 前的主张：AI 原生时代的用人约束（学习者提出，我的判定）

**他的主张**：承认 Rust 程序员不好招，但「未来云原生、AI 原生时代，我们要招的不是程序员，而是更优秀的 AI」；并明确询问我是否认同。

**我的判定：方向认同，三处必须收窄**（完整合成见 [[ai-native-architecture-constraints|AI-Native Architecture Constraints]]）：
1. **责任与合规不可外包**：实名 / 内容安全 / 审计必须有**人**签字与值守；
2. **成本换形态而非消失**：人＝固定成本 + 容量上限；AI＝**随用量增长的可变成本 + 反馈回路**（正是他第 2 条回答里"先坏"的那条曲线）；
3. **新增单一模型依赖**：语言可行性若依赖某模型当前能力，模型涨价/下架/回能都会传导成架构风险。

**更站得住的表述**：「在建造者以 AI 为主的项目里，选型的第一性约束从**人类人才池**转移到**建造者可验证性 × 单位产出边际成本**；人类角色收窄为**验收、担责、判断**——程序员从生产者变成验收者与责任人。」
## Q4 已答：可度量后果 + 两处收窄

**他给的答案**：①生态不完善的 token 高消耗属**开发期一次性投入**，ROI 服务长期（不是每条用户动作的成本）；②可验证性的收益是**写代码阶段不出错代码 → 避免 CI/CD 上线后出生产事故**；③内存基线 200MB（含压测）长期不受影响；④「暂时没有其他要补充的了」。

**两处必须收窄（否则评审里会被打）**：
1. **「不会出现错误代码」是绝对断言** → 应改为：「Rust 在**编译期挡住一整类缺陷**（内存安全 / 类型安全 / 数据竞争 / 穷尽匹配），**显著降低线上事故概率**；但**不覆盖**业务语义、需求理解与算法逻辑错误。」**它抬下限，不抬上限。**
2. **内存 200MB 要带压测条件**（并发数、数据量、Agent 并发数）才可复核；且 200MB 主要由常驻决定，**Agent 并发上升时的内存曲线要单独给一条数据**。

**可度量链（建议写进 ADR）**：编译期捕获数 → CI 失败率 → **线上事故数 / 回滚次数 / MTTR**；成本侧：开发期一次性 token 总量（摊销）· 运行期 ¥/发帖、¥/Agent 回复、¥/GB·月。
## Q5 已答（推翻条件）+ S3 闸门：通过（2026-10-05）

**他给的推翻条件（原话要点）**
1. **迭代速度成为首要约束**：「当产品迭代需要非常快速时，可验证的就是 TypeScript 的优势……Rust 的一大短板是需要反复完整编译」；并自评「我现在单人开发具备一定敏捷性，但敏捷开发的核心是快速迭代功能点，**这一状态是可被推翻的**」。
2. **出现 AI 原生编程语言**：「具备 Rust 的大部分特性，同时弥补其缺陷」→ 他会推翻 Rust。
3. **生态不是推翻理由**：「随着 AI 的进步，不止我一个人会去完善 Rust 生态」——生态会收敛，不构成推翻。
4. **监控项**：「工具链方面，主模型不太擅长使用 Rust」——**这正好印证**了本轮早先标出的「单一模型依赖」风险；目前靠编译期的确定性对冲。

**S3 闸门：通过**

| 通过标准 | 结果 |
|---|---|
| Context 约束 ≥3 条且无推销词 | ✅ 4 条，全为约束 |
| Decision 一句话可执行 | ✅「我们将……建立在 Rust 生态之上」 |
| 备选 ≥2 且各自写出代价 | ✅ Python（缩进歧义 + 冗余文件）/ Rust（token + 改造摩擦） |
| 代价 ≥1 | ✅ token 成本、改造摩擦 |
| 可度量后果 ≥1 | ✅ 编译期捕获 → CI 失败率 → 线上事故 / 回滚 / MTTR |
| **推翻条件 ≥1** | ✅ 迭代速度约束翻转 / AI 原生语言出现 |
| ≤2 页 · 有 Status | ✅ accepted |

**否决项检查**：备选 <2？否 · 没有代价？否 · **没有推翻条件？否** → **通过。**

**一句总结这份 ADR 的策略**：**用工具链的确定性，对冲模型的随机性**——这也是他全部选型逻辑的内核。当出现一种语言能同时给「高信号质量 + 低迭代时延」时，这个对冲就不需要了，所以「AI 原生语言」是有效的推翻条件。
